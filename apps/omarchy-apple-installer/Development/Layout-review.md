# Layout and experience review

Status: **Approved and implemented locally** in `feature/installer-audit-simulation`.

| Priority | Current issue | Proposed improvement | Acceptance check |
| --- | --- | --- | --- |
| 1 | The authorization sheet mixes a centered small title, left-aligned body and fields, and right-aligned actions. This makes the box feel misaligned. | Use one left edge with a 24-point inset, a 20-point title, 16-point spacing within related content and 24 points before the footer. Increase the sheet from 380 to roughly 440–460 points wide. | Title, explanatory text and field labels share a left edge; no clipping in dark or light appearance. |
| 1 | Simulation omits the account fields, so its authorization box is much shorter than the real form. | Render a read-only fake account and masked password placeholder in simulation, using the same layout as the live form. | Real credentials are never requested; rejection and working states retain identical geometry. |
| 1 | The action opening authorization and the action submitting credentials both say Install, making the transition ambiguous. | Keep Install on the reviewed plan; use “Authorize & install” on the sheet. Use “Authorize Recovery” for the restricted retry. | Each action clearly describes what happens next; retry cannot replay disk work. |
| 1 | A busy spinner and validation errors can shift the authorization content. | Reserve a status row, place errors next to the relevant fields, and keep both footer buttons at the same height and baseline. | Invalid credentials, submission and retry do not move the footer or lose entered account name. |
| 1 | Size arrows make precise allocation tedious. | **Implemented:** editable GB field; green checkmark applies, red cross cancels. Return applies and Escape cancels. Inline validation retains invalid drafts. Approval is blocked while editing. | Exact byte values survive unchanged edits; cancel preserves the current plan; applying a changed size requires a new plan and acknowledgement. |
| 2 | Capacity, release and internal disk identifiers compete with the main decision. | Emphasize the allocation bar, selected size and backup acknowledgement. Keep technical identifiers in the details disclosure. | The user can identify retained macOS space and selected Omarchy space without interpreting device IDs. |
| 2 | The authorization step repeats context without a compact statement of the approved allocation. | Add a brief read-only summary of the approved Omarchy size above the account fields. | Summary uses the approved plan, never a stale draft. |
| 2 | Error text sometimes promises that nothing changed or suggests a restart despite uncertainty. | Adopt the evidence-qualified wording in the message table. Pair unknown outcomes with a copy/view-record action. | Post-submission uncertainty never offers an unsafe fresh installation. |
| 2 | Some recovery instructions are lengthy and must survive shutdown. | Use short numbered steps, a prominent copy action and a reminder to save them on another device. | Instructions remain available if shutdown fails or is cancelled. |
| 2 | Dark and light appearances need consistent control contrast. | Preserve the Omarchy dark default in simulation, and validate the same spacing and semantic colors in light appearance. | Apply/cancel remain recognizable by symbol and accessible name, not color alone. |

The authorization proposal should be reviewed in normal, rejected-credential, working and Recovery-retry states at both 640×600 and 780×850 window sizes, with keyboard navigation and VoiceOver. The simulator now uses the same field layout, with read-only dummy values. Dark and light authorization sheets were visually inspected; the window minimum enforced a 640×632 outer size when 640×600 was requested. Native accessibility inspection confirmed account labels and inline credential rejection. VoiceOver speech and physical installation were not exercised.

The authorization layout, message changes, technical-details disclosure and copyable installation record are implemented. See [the full message table](Message-review.md) for the approved baseline and implementation notes.
